High REL-002 Containers without memory limits 1 resource affected

Why it matters

A container with no memory limit can grow until the node itself runs out of memory. When that happens Kubernetes kills pods on that node, often ones that had nothing to do with the leak.

How to fix it

Set a memory limit on every container. Start at roughly 1.5 to 2 times the memory request and adjust from real usage.

resources:
  requests:
    memory: 256Mi
  limits:
    memory: 512Mi

Medium REL-004 Workloads without liveness probes 1 resource affected

Why it matters

Without a liveness probe, a container that hangs or deadlocks keeps running. Kubernetes believes it is healthy, so nothing restarts it until a person notices.

How to fix it

Add a liveness probe that fails when the process is stuck. Keep it cheap and do not make it depend on other services.

livenessProbe:
  httpGet:
    path: /livez
    port: 8080
  periodSeconds: 10
  failureThreshold: 3

Medium REL-005 Multi-replica workloads without a PodDisruptionBudget 1 resource affected

Why it matters

Without a PodDisruptionBudget, a node upgrade or scale-down can take every replica of a service offline at once. Running several replicas does not protect you during maintenance unless a budget says how many must stay up.

How to fix it

Create a PodDisruptionBudget for each multi-replica workload, selecting its pods by label.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: api

Medium REL-010 Images using the latest tag or no tag 1 resource affected

Why it matters

With latest you cannot tell which version is running, two replicas can run different code, and a rollback has nothing to roll back to. A pod restart can silently pull in an untested build.

How to fix it

Deploy a specific version tag or, better, an image digest. Have CI write the tag into the manifest on every release.

Low REL-007 Deployments with no HorizontalPodAutoscaler 3 resources affected

Why it matters

A Deployment with a fixed replica count cannot absorb a traffic spike. It either falls over under load or you pay for peak capacity around the clock.

How to fix it

Add a HorizontalPodAutoscaler to services whose load varies. Fixed-size background workers can be left as they are.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

Why it matters

cluster-admin can read every secret and delete every workload in the cluster. Each person or service account holding it is a single stolen credential away from a full compromise.

High SEC-004 Secrets passed as plain environment variable values 1 resource affected

Why it matters

A password written straight into a manifest is visible to anyone who can read the Deployment, and it is copied into Git history, CI logs and every kubectl describe output.

How to fix it

Move the value into a Secret (or an external secret manager) and reference it. Then rotate the credential, since the old value has already been exposed.

env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: db-credentials
        key: password

Medium SEC-005 Namespaces with no NetworkPolicy 2 resources affected

Why it matters

With no NetworkPolicy, every pod in the cluster can connect to every pod in this namespace. One compromised container can reach your databases and internal APIs directly.

How to fix it

Start with a default-deny policy per namespace, then allow the specific traffic each service needs.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}
  policyTypes: ["Ingress"]

Low SEC-008 Workloads using the default ServiceAccount with token automount 1 resource affected

Why it matters

Every pod on the default ServiceAccount shares one identity and gets its API token mounted, needed or not. Any permission later granted to that account is granted to all of them at once.

How to fix it

Give each workload its own ServiceAccount, and turn off token mounting for pods that never call the Kubernetes API.

spec:
  serviceAccountName: api
  automountServiceAccountToken: false

Recovery Can you get your data back?

High REC-003 StatefulSets with no VolumeSnapshot or backup schedule covering them 1 resource affected

Why it matters

These StatefulSets store data on volumes that no backup schedule includes and no recent snapshot covers. If the volume is lost or the data is corrupted, there is nothing to restore from.

How to fix it

Include the namespace in a Velero schedule with volume backups, or take scheduled VolumeSnapshots of each data volume.

apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: daily
  namespace: velero
spec:
  schedule: "0 2 * * *"
  template:
    includedNamespaces: ["*"]
    snapshotVolumes: true
